## 二、阻断级问题（P0，必须先解决才能开工）

### P0-1　技术栈与真实工程根本冲突 🔴

**证据**

- 规划文档 §十一（第 366 行）：`框架 | React 18 + Vite + TypeScript | 用户现有栈（Vite）`
- 可视化 HTML 第 186 行：同款表述
- 仓库真实状态：
  - `package.json` 第 13 行依赖 `@lynx-js/react ^0.126.0`，构建脚本为 `rspeedy build/dev/preview`（第 6–10 行）
  - `AGENTS.md` 第 3 行：`You are an expert in JavaScript, Rspeedy, and Lynx application development`
  - `src/App.tsx` 使用 `<view>` / `<text>` / `bindtap` —— 这是 Lynx 原生组件，不是 Web DOM
  - 类型依赖为 `@types/react ^19`，`biome` 做 lint，`bun.lock` 管理依赖

**影响**：文档里"沿用现有 Vite 技术栈"的前提**不成立**。这直接推翻 §十、§十一 的整套实现路径：
- `localStorage`、`Zustand + persist`、`PWA`、`mermaid.js` 均为浏览器 Web API / DOM 库，**Lynx 原生运行时（iOS/Android）不提供**
- 目录结构 `src/pages/...` 的约定也与 Lynx 工程结构不符

**必须先拍板**：本项目目标是 **A. H5（手机浏览器网页）** 还是 **B. Lynx 跨平台 App（可同时出 Web+原生）**？
- 若 A：需要**另起工程**，当前 nijapl 工程要迁移/新建 Vite 项目，文档 §十一 才成立
- 若 B：文档 §八（发音）、§九（脑图）、§十一（存储/状态）**全部要重写**，改用 Lynx 的能力（TTS 走原生桥、图谱走 Lynx 自绘/SVG、存储走 Lynx 本地存储）

这一条不定，后面所有技术评审都是空谈。

### P0-2　数据源文件全部缺失，且"例句"是数据黑洞 🔴

**证据**

- 文档第 5 行声明数据来源：`JLPT-N3-词汇总表-Anki.csv`、`JLPT-N3-第一/二/三阶段词汇表.md`、`JLPT-N3-语法句型总表.md`、`JLPT-N3-备考计划.md`
- 在仓库内全量检索（排除 `node_modules`）**未找到任何一个上述文件**，仅存在文档自身
- 因此 §二「数据基础」的 **992 词 / 3 阶段 / 41 模块 / 230 句型 / 20 周次组** 全部**无法核验**

**更致命的是例句缺口**

- §二 第 25 行：词条 CSV 仅六字段 `假名 / 汉字 / 词性 / 阶段 / 模块 / 中文` —— **没有例句字段**
- §八 GRAMMAR 表（第 265–272 行）：`pattern / connection / scene / week / level` —— **也没有例句字段**
- 但文档大量功能依赖例句：
  - P2 卡片背面「例句整句可点朗读」（第 184 行）
  - P3 分区块「例句（TTS）」（第 190 行）
  - P5「例句（TTS）」（第 193 行）
  - 跳转规则「例句含生语法 → 语法高亮 → 点进 P5」（第 159 行）——**没有"例句→语法"映射，这条规则根本无法计算**
  - ER 图 `WORD }o--o{ GRAMMAR : "例句引用"`（第 238 行）——**关联经由例句，却没有 SENTENCE 实体**

**判断**：例句（含中文翻译 + 语法点标注）是这个产品的**内容底座**，目前既无数据、也无模型、更无生产成本估算。这是比技术栈更本质的风险 —— 992 词 × 例句 + 230 句型 × 例句，本身就是一个独立的内容工程项目。

### P0-3　运行时能力假设未验证 🔴

即便不考虑 Lynx/H5 之争，以下假设在真实移动端有明确坑，文档只覆盖了一部分：

| 能力 | 文档假设 | 现实风险 |
|------|---------|---------|
| TTS | Web Speech API，iOS/Android/Chrome 均支持（第 353 行） | **微信内置浏览器（X5/WKWebView）普遍阉割 `speechSynthesis`**。一个"分享给日语学习者"的 H5，大概率在微信里被打开 → 点了没声音 |
| 读音选择 | P9 可切换「训读/音读」（第 358 行） | `speechSynthesis` **无法指定音读/训读**，只能照文本读；要控制必须为每个词准备多读音数据，而 CSV 只有一列假名 → **该功能当前不可实现** |
| 音色挑选 | 优先 Google 日本語/Otoya/Kyoko（第 354 行） | `speechSynthesis.getVoices()` 异步、跨平台音色名不一致，iOS 上根本不是这些名字 → 需按 lang 前缀模糊匹配 + `voiceschanged` 兜底 |
| 脑图 | mermaid.js（第 369 行） | 仅 Web 可用；且 mermaid 打包体积大，mindmap 渲染在移动端性能存疑 |
| 存储 | localStorage 足够（第 368 行） | 仅 Web；Lynx/原生不可用 |

## 三、需求与信息架构漏洞（P1）

### P1-1　需求 5（脑图）入口被埋，且站点图断边 🔴

- 文档自己写了 P6 全景脑图的入口是「P1 长按、**P0 入口**」（第 200 行）
- 但 §四 站点地图（第 78–113 行）**没有任何 P0 → P6 的边**
- 现状入口只剩：P1 **长按**模块（隐藏手势）、P3/P5 的页内按钮 → **新用户几乎不可能发现脑图**
- 更讽刺的是：底部 5 个 Tab 里，**P4 语法列表**（而"语法"并非 5 条原始需求之一）占了 1 个 Tab，**而作为核心需求 5 落点的 P6 一个 Tab 都没有**

> 建议：要么给 P6 一个 Tab（挤掉或合并 P4），要么在 P0 首页放一个显性卡片入口，二选一，不能只靠"长按"。

### P1-2　阶段数不自洽，冲刺期会算出 NaN 🔴

- §二 表格（第 25 行）：阶段 = **3**
- §二 PM 备注（第 31–32 行）与 §六 P1（第 176 行）：应渲染 **4 个阶段节点**（含冲刺期）
- §八 STAGE.id（第 245 行）包含 `冲刺期`
- 但 **P1 解锁规则「上一阶段完成度 ≥ 80% 才解锁下一阶段」**（第 178 行）遇到冲刺期（0 个词）时：完成度 = 0/0 = **NaN**，逻辑未定义
- 且状态机 `已掌握 --> [*]: 全部阶段完成`（第 222 行）对一个"只属于某阶段"的词而言语义错误

**建议**：STAGE 显式区分 `hasContent`（新词阶段）与 `reviewOnly`（冲刺期），进度计算对 `wordCount === 0` 做短路，解锁规则改为「上一**含词**阶段完成度 ≥ 80%」。

### P1-3　状态术语不一致 & 状态数写错

| 位置 | 问题 |
|------|------|
| 第 177 行 | 标题写「节点**四态**」，实际列了 **5 个**（🔒⬜🟡✅🔴） |
| 第 177 行 vs 第 216 行 | P1 用「🔴**需复习**」，状态机用「**需强化**」—— 同一概念两个名字 |
| 第 187 行 | P2 有「**左滑跳过**」手势，但状态机（第 210–227 行）**没有"跳过"状态**，用户跳过后的词怎么记？未定义 |
| 第 158 行 | 规则表用 `word.wrongCount >= 2`，流程图用「累计错误≥2」，而 §八 PROGRESS 字段是 `wrongCount` —— 基本一致，但"累计"是永久还是按会话？需明确 |

### P1-4　未建模的交互状态（会导致功能做不出来）

- **断点续学**：P0 有「继续学习卡 · 上次停在第二阶段第 12/27 词」（第 170 行）→ 但数据模型没有任何"学习位置/会话"实体，无法实现
- **连续打卡 N 天**（第 169 行）→ PROGRESS 无 `lastStudyDate`，无打卡记录表，无法实现
- **今日任务**（第 172 行：新学 20 + 复习 35 + 语法 2）→ 无"每日任务/配额"模型

## 四、一致性与细节问题（P2）

1. **MD 与 HTML 两版多处不一致**（同一份规划两个版本，需指定唯一事实源）：
   - `WORD.stageId`：MD 第 262 行**有**，HTML 第 341–348 行**没有**
   - `GRAMMAR.level`：MD 第 271 行**有**，HTML 第 349–355 行**没有**
   - 状态机出口：MD 第 222 行「**全部**阶段完成」 vs HTML 第 314 行「**该**阶段完成」
   - 冲刺期：HTML 脑图（第 402–404 行）**有**冲刺期分支，MD 脑图（第 286–325 行）**没有**
2. **周次口径冲突**：§二 第 28 行「230 句型分 **20 个周次组**」，但备考计划是 **26 周**（第 23–26 周为冲刺期）→ 20 组 如何映射到 26 周？需说明。
3. **验收标准不可控**：§十三 第 410 行「点卡片热区 **200ms 内**出声」—— `speechSynthesis` 冷启动 + 异步音色加载，200ms 不保证；建议改为"点击后立即给出视觉/触觉反馈，音频就绪后播放"。
4. **「日语音色正确」不可自动验收**（第 410 行）—— 需人工听感验收，或在验收表标注为人工项。
5. **词性判定依赖 CSV 编码**：规则 `pos ∈ {五, 一, サ, 不}`（第 161 行）用单字缩写匹配，CSV 里若写「五段动词」也能命中，但若写「動詞」则漏判 → 建议改为显式枚举映射表。
6. **P8 出现在 IA/站点图中，却不在 v1.0 范围**（§十二 第 395 行 v1.0 只含 P0–P7）→ 建议图中标注「v1.1」，避免误读。

## 五、做得好、应保留的部分 🟢

1. **需求 → 功能映射表**清晰，5 条需求无遗漏，且明确标注 MVP 归属。
2. **跳转规则表（jumpRules.ts）**是整个文档最有价值的设计：把"适时跳转"从模糊需求翻译成 6 条可配置条件，且给了状态字段，工程可直接翻译成配置。
3. **卡片三档自评 + SRS 状态机**方向正确，间隔序列（10min/1d/3d/7d/15d/30d）合理。
4. **发音降级设计**（音色缺失 → 提示装语音包 / 预置 mp3）思路对，明确写了"不出现点了没声音"这一体验红线。
5. **站点地图 + 关系要点**点明了「P2 是流量枢纽」。这个洞察是对的，后续设计应围绕它收敛而非平铺 10 个页面。
