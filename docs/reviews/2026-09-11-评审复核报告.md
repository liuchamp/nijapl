## 二、P0-1：`todayNewCount` —— 缺陷真实存在，但"恒为 0"是错的

### 2.1 存在性判定：✅ 缺陷成立（已实测）

**实测数据**（`tests/audit/p0-today-new-count.audit.test.ts`，走 Study 页真实链路）：

```
markPresented 之后        :: todayNewCount=0  progress={state=学习中, seen=true, history=0}
submitSelfEval(不认识)之后 :: todayNewCount=0  progress={state=需强化, seen=true, history=1}
同一词二次自评之后        :: todayNewCount=0  history=2
换第二个新词走同样链路    :: todayNewCount=0  history=1
```

失败断言（vitest 真实输出）：
```
AssertionError: expected +0 to be 1
 ❯ tests/audit/p0-today-new-count.audit.test.ts:118:42
    118|     expect(read().session.todayNewCount).toBe(1)
```

### 2.2 原由（完整因果链）

1. `src/engine/srs.ts:53-63` 的 `applyPresented` 在卡片首次展示时置 `seen: true`。守卫是 `if (p.state !== '未学') return p`，首次进入的词必定命中置位分支，**守卫不构成逃生口**（原报告曾疑虑这点，实际不成立）。
2. `src/pages/Study/index.tsx:71-79` 的 `useEffect` 在 `word !== undefined` 时调用 `studySession.presentCurrentCard()` → `markPresented`，发生在用户自评**之前**。
3. `src/store/actions.ts:233` 取 `existing = state.progress[targetId] ?? initialProgress(targetId)`，此时读到的是**已被 `markPresented` 污染**的对象（`seen === true`）。
4. `src/store/actions.ts:250-252` 判据 `existing.seen ? 不变 : +1` → 永远走"不变"。

**根因不是写错，是同一个裁决没全域落地**：`src/engine/jumpRules.ts:14-29` 的 Ruling 1 早就写明"`seen` 的语义收敛为『卡片展示过』，**不再参与**首次遇词判定"，J1 已改用 `history.length === 0`，而 `submitSelfEval` 仍用 `existing.seen`。

### 2.3 但"恒为 0"不成立 —— 原报告的推理断点

原报告**没有全局搜索 `submitSelfEval` 的调用点**，只看到 Study 一条链路就外推成全局结论。实际有第二个调用点：

`src/pages/Quiz/index.tsx:89`：
```tsx
appActions.submitSelfEval(question.wordId, correct ? '认识' : '不认识')
```

它**从不调用 `markPresented`**，且 `src/services/quiz.ts:69` 的题源是全词库、无"已学"过滤。实测对照链路：

```
未 markPresented 直接自评之后 :: todayNewCount=1   ← 能 +1
```

**精确结论**：

| 链路 | 行为 |
|------|------|
| P2 词汇学习（唯一走 `markPresented`） | **恒不递增** |
| P8 自测（Quiz 页直连） | 未评估过的词**会 +1**（口径污染：把"自测首次作答"算成"新学"） |

所以计数**可以**非 0，只是计的完全不是"新学"。

### 2.4 修法验证：方案 A 有效，且**不需要**按日去重

原报告方案 A（`existing.history.length === 0`）经跨天实测验证正确。`Progress` 确有 `history` 字段（`src/types/progress.ts:28`，初值 `[]`），类型前提成立。

跨天投影实测（`tests/audit/p0-cross-day.audit.test.ts`，注入 `T1 = T0 + 86400000`，`lastStudyDate` 由 `2026-09-11` → `2026-09-12` 佐证跨天生效）：

| 场景 | 方案 A 结果 | 是否正确 |
|------|------------|---------|
| 跨天 + 全新词 | 1 | ✅ |
| 跨天 + 复习旧词（基准 1） | 保持 1，不重复计 | ✅ |
| 跨天 + 全新语法点 | 1 | ✅ |
| 跨天 + 再评已评过的语法点 | 0 | ✅ |
| 跨天 + 依次评 G3→G4 | 1 → 2（填满 DAILY_GRAMMAR_GOAL） | ✅ |

**机理**：一个目标的 `history` 只会从空变非空**一次**，首次评估只发生在唯一的一天。且 `applySkip` 刻意不写 `history`（Ruling 1，`srs.ts:146-154`），故"首次评估"必然只落在唯一一天，天然蕴含"当日首次"，与 `rollSessionDay` 的每日归零正交 —— 前者判定"是不是第一次被评估"，后者判定"今天学了多少"，组合恰好等于"今日新学"。

> ⚠️ **不要引入 `lastEvalDate` / `todayEvaluatedIds`**。实测证明无必要，只会增加持久化字段与迁移成本。按日去重是**方案 B（展示即计新学）**的需求，不是方案 A 的。（该提议由工程师提出、经 QA 跨天实测后由工程师本人主动撤回。）

**⚠️ 方案 A 的空值问题**：曾认为"只需在判据处加 `?.` 防御"，经第三轮实测**更正** —— 崩溃点在 `applySelfEval → pushRecord(p.history)`（`srs.ts:21-29` 的 `[...history]`），判据还没执行到就先炸；且**现状代码用 `seen` 判据时同样崩**。所以这是**既有缺陷**，不是方案 A 引入的回归。详见第七节 A。

## 四、P1-2：图谱 O(n²) —— 现象存在，但三个细节都错了

1. **复杂度标签错**：第一层是 O(r)（r = 该词 `related` 条数，通常 0~3），第二层 O(n)×O(r̄)。整体 **O(n·r)**，r 为常数级 → 近似线性，**不是 O(n²)**。

## 七、原报告漏掉的真实问题

### A.（P2，既有缺陷）`readProgress` 零净化 —— 脏数据下自评完全失效

`src/store/persistence.ts:84-89`：
```ts
function readProgress(value: unknown): Record<string, Progress> {
  if (!isRecord(value)) {
    return {}
  }
  return value as Record<string, Progress>
}
```
对比同文件 `readSession`（91-109）、`readSettings`（111-125）的逐字段 `readString/readNumber/readBoolean` 回落 —— **`progress` 分片完全没有逐字段净化**，只做 `isRecord` 就直转。

**实测**（`tests/audit/p0-persistence-dirty.audit.test.ts`，10 用例全绿，即全部为已证实事实）：

| 场景 | 实测结果 |
|------|---------|
| `migrateState` 后 | `progress.w-01.history = undefined`（未净化）；control 组 `session.todayNewCount=0`、`settings.rate=1`（已净化） |
| 脏数据进 store | version 匹配 & 不匹配**两条路径都通** |
| **现状代码（seen 判据）** | 抛 `TypeError: ...reading 'length'`，抛错后 `state` 仍为「学习中」→ **自评完全失效** |
| 只加判据防御 `(existing.history?.length ?? 0)` | 判据 `delta=1` 算出来了，但随后 `applySelfEval` **仍抛** |
| 净化 `history=[]` 后 | `threw=false`，`state=需强化`，SRS 正常推进 |
| 非数组脏值 `history:'oops'` | 裸写法 `length=4` → 静默不 +1（**不抛错但结果错**） |

**三条关键更正**（推翻"方案 A 引入新风险"的初判）：

1. **崩溃点不在判据，而在判据之前的调用** —— 不同入口的首个崩溃点不同（已用 node 对照片验证 V8 报错消息）：

   | 入口 | 脏 `history` 首个崩溃点 | 报错 |
   |------|----------------------|------|

**⚠️ 修法的关键落点：净化必须加在 `merge`，补 `readProgress` 是无效的**

`node_modules/zustand`（**4.5.7**）`esm/middleware.mjs:376-388` 原文：
```js
if (typeof deserializedStorageValue.version === "number" && deserializedStorageValue.version !== options.version) {
  if (options.migrate) { return options.migrate(...); }
  ...
} else {
  return deserializedStorageValue.state;   // ← 版本一致：直返原始 state，migrate 不执行
}
```
而 `createPersistOptions`（`persistence.ts:154-168`）只把 `migrateState` 挂在 `migrate` 上（159 行），**没有自定义 `merge`** → 真实 rehydrate（版本一致）走"原始 state → 默认浅合并 → 进 store"，`migrateState` 里所有净化**一次都不执行**。**只补 `readProgress` 等于白补**（单测直接调 `migrateState` 会绿，但真实路径走不到）。

正确写法（`persistence.ts` 一处 3 行，复用现有 `migrateState`）：
```ts
    migrate: (persisted: unknown) => migrateState(persisted),
    // zustand 仅在 version 不一致时调用 migrate（zustand/esm/middleware.mjs:376-388），
    // 版本一致的存储损坏路径不经过净化，故在 merge 内再净化一次。
    merge: (persisted, current) =>
      persisted === undefined ? current : { ...current, ...migrateState(persisted) },
```
> `persisted === undefined` 守卫不能省：首次安装 / 空存储时走 `merge(undefined, current)`，否则 `migrateState(undefined)` 返回全默认值会覆盖 `current`。

同时 `readProgress` 内补 `history: Array.isArray(value.history) ? value.history : []`。**必须用 `Array.isArray`，不能只判真值**：`history: 'oops'` 时 `'oops'.length === 4` → 静默认定为"已评估过"不 +1，**不抛错但结果错，比崩溃更难查**。

判据处另加 `(existing.history?.length ?? 0) === 0` 作零成本双保险。**禁止**用 `existing.history!.length` 绕类型报错。

**探针 store 实测佐证**（`tests/audit/p0-persist-merge.audit.test.ts`，复用项目真实 `createPersistOptions`，只覆盖 name/migrate/merge 并埋计数器，未改 `src/`）：

[AUDIT] version 一致  :: migrate=0 次 | merge 收到 session.todayNewCount="oops"（未净化即原始脏值）
[AUDIT] version 不一致 :: migrate=1 次 | merge=1 次
