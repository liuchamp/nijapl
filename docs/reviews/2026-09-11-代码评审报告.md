## 二、阻断级问题（P0）

### P0-1　`todayNewCount` 在正常链路下恒为 0 🔴

「今日新学」计数（首页进度环 + `selectTodayStats.newCount`）依赖 `submitSelfEval` 中的这段逻辑，而它与 `markPresented`（展示即转态）的执行顺序存在冲突，导致计数永远无法递增。

**证据**（`src/store/actions.ts` 第 225–263 行，`submitSelfEval`）：

```ts
submitSelfEval(
  targetId: string,
  selfEval: SelfEval,
  now?: number,
): JumpDecision[] {
  const at = now ?? Date.now()
  const state = get()
  const word = repository.getWordById(targetId)
  const existing = state.progress[targetId] ?? initialProgress(targetId)
  // ...
  const next = applySelfEval(existing, selfEval, at)
  const session = rollSessionDay(state.session, at)
  set({
    progress: { ...state.progress, [targetId]: next },
    session: {
      ...session,
      todayNewCount: existing.seen
        ? session.todayNewCount
        : session.todayNewCount + 1,
    },
    // ...
  })
```

而 `markPresented`（第 205–223 行）在卡片首次可见时已把 `seen` 置为 `true`：

```ts
markPresented(targetId: string, now?: number): void {
  const at = now ?? Date.now()
  const state = get()
  const existing = state.progress[targetId]
  if (existing === undefined) {
    set({
      progress: {
        ...state.progress,
        [targetId]: applyPresented(initialProgress(targetId), at),
      },
    })
    return
  }
  // ...
}
```

`applyPresented`（`src/engine/srs.ts` 第 53–63 行）明确置 `seen: true`：

```ts
export function applyPresented(p: Progress, now: number): Progress {
  if (p.state !== '未学') {
    return p
  }
  return {
    ...p,
    state: '学习中',
    seen: true,          // ← 展示即转态，seen 恒为 true
    nextReview: now + intervalAt(0),
  }
}
```

**正常学习链路**（`src/pages/Study/index.tsx` 第 71–79 行）：

```ts
useEffect(() => {
  if (word === undefined) {
    return
  }
  studySession.presentCurrentCard()   // → markPresented → seen = true
  setEffect(studySession.evaluateSceneEffect(word))
  // ...
}, [word?.id])
```

**推理链**：`presentCurrentCard` 先把 `seen` 置 `true` → 用户自评触发 `submitSelfEval` → `existing.seen === true` → `todayNewCount` 走 `?` 分支，**永不 +1**。

**影响**：首页「今日任务」进度环的「新学」分母永远是 `0/20`；`selectTodayStats.newCount` 恒为 0；`MePage` 的「今日新学」统计也恒为 0。这是用户可见的核心功能失效。

**根因**：`todayNewCount` 的判定错误地复用了 `seen` 字段。「新学」的语义应当是「该词**今天第一次被评估**」（等价于「从『未学/学习中』态提交了首次自评」），而非「是否展示过」。`seen` 在展示阶段就被污染，无法再充当「新学」判据。

**建议修法**（二选一）：

1. **方案 A（推荐）**：在 `submitSelfEval` 里用「评估历史为空」判断首次评估，即 `existing.history.length === 0`。这与 J1「首次遇词」的语义裁决（Ruling 1：`isFirstEncounter = history.length === 0`）完全一致，语义统一：

```ts
todayNewCount: existing.history.length === 0
  ? session.todayNewCount + 1
  : session.todayNewCount,
```

2. **方案 B**：把「新学计数」下沉到 `markPresented`（展示即转态即视为「今天学了新词」），`submitSelfEval` 不再计 `todayNewCount`。此方案语义为「展示计新学」，与「自评计新学」的产品口径不同，需与产品确认。

无论哪种，**必须补一条单测**锁定：`markPresented → submitSelfEval('不认识')` 后 `session.todayNewCount === 1`；二次自评同一词 `todayNewCount` 不再递增。

## 三、重要问题（P1）

### P1-1　多页面 `useAppStore((snapshot) => snapshot)` 全量订阅，破坏 selector 约定 🟡

`src/store/hooks.ts` 第 16–19 行明确声明了 selector 契约：

```ts
export function useAppStore<T>(selector: (state: AppState) => T): T {
  return useStore(appStore, selector)
}
```

并在文件头注释（第 9–11 行）强调：

```ts
 * - `useAppStore(selector)`：通用选择器（**selector 必须返回稳定引用或原始值**，
 *   不要在其中构造新对象 / 新数组，否则会触发无限重渲染）；
```

但以下页面直接返回了整个 state 对象：

| 文件 | 行 | 代码 |
|------|----|------|
| `src/pages/Home/index.tsx` | 31 | `const state = useAppStore((snapshot) => snapshot)` |
| `src/pages/Study/index.tsx` | 43 | `const state = useAppStore((snapshot) => snapshot)` |
| `src/pages/Review/index.tsx` | 31 | `const state = useAppStore((snapshot) => snapshot)` |
| `src/pages/VocabDetail/index.tsx` | 30 | `const state = useAppStore((snapshot) => snapshot)` |

**问题**：zustand v4 的 `useStore` 用 `Object.is` 比较 selector 返回值。`snapshot => snapshot` 返回的是 store 顶层 state 对象，而每次 `set` 都会产生一个新的顶层对象（如 `actions.ts` 里的 `set((state) => ({ runtime: {...} }))`），因此**任何一次状态变更**（包括 `runtime.detailSheet.visible`、`sessionWrongCount` 这类与页面无关的易失状态）都会触发这四个页面**全量重渲染**。

以 `StudyPage` 为例：它自己调用 `appActions.openDetailSheet(...)` 会 set `runtime.detailSheet`，立即引发整页重渲染；而 `HomePage` 在 `startStudy` 或其它页面任何写操作时，也会被无谓地重渲染。

**影响**：性能隐患（尤其 Lynx 原生端渲染成本高），且与项目自身「selector 必须返回稳定引用」的红线相悖，属于「代码写出了正确功能、但订阅粒度失控」的典型问题。

**建议**：改为按需订阅稳定分片或原始值。这几个页面其实大多只用 `state.progress` / `state.session` / `state.runtime` 中的少数字段，可改用已提供的 hooks（`useProgressMap` / `useSession` / `useRuntime`）或精确 selector。例如 `HomePage` 需要的 `session.moduleId` 与 `progress`，可改为：

```ts
const session = useSession()
const progressMap = useProgressMap()
```

再由这两个稳定分片驱动现有的 `selectTodayStats` / `selectContinueTarget` 等纯函数（它们本就接受 `state` 参数，但传稳定分片即可）。注意：`selectTodayStats` 等签名是 `(state: AppState, now)`，若只传分片需相应调整选择器签名，或封装成「按字段订阅」的组合。

### P1-2　`graph/view.ts` 关联词收集为 O(n²)，且例句扫描未走索引 🟡

`src/engine/graph/view.ts` 第 57–85 行 `collectRelatedWords`：

```ts
function collectRelatedWords(
  word: Word,
  all: Word[],
): Array<{ word: Word; type: string }> {
  const result: Array<{ word: Word; type: string }> = []
  const seen = new Set<string>()

  for (const rel of word.related ?? []) {
    const target = all.find((w) => w.id === rel.toId)   // ← 每个 rel 一次 O(n)
    // ...
  }

  for (const other of all) {                              // ← 外层 O(n)
    // ...
    for (const rel of other.related ?? []) {             // ← 内层再 O(n)
      if (rel.toId === word.id && !seen.has(other.id)) {
        // ...
      }
    }
  }
  return result
}
```

同样的模式出现在 `buildWordView`（第 117–138 行）和 `buildGrammarView`（第 187–208 行）中，用 `data.sentences.some(...)` / `data.grammars.find(...)` 做全量扫描。而 `DataRepository`（`src/data/repository.ts`）已经建好了 `wordById`、`sentencesByWordId`、`sentencesByGrammarId` 等索引，但图谱构造层**没有复用这些索引**，反而对原始数组反复 `find`/`some`。

**影响**：当前数据量（N3 约千词、数百句）下性能可接受，但这是「数据规模增长即退化」的隐患；且与 `repository` 已提供的 O(1) 查询能力相矛盾——引擎层刻意「零端口依赖」而绕过了仓库索引。

**建议**：图谱构造入参 `GraphSourceData` 目前是 `BuildData`（裸数组）。可改为传入 `DataRepository` 实例（或其只读接口），在 `collectRelatedWords` 里用 `wordById` 做 O(1) 查找，例句/语法关联改用 `sentencesByWordId` / `sentencesByGrammarId`。这样既消除 O(n²)，也让引擎与数据层索引统一。若坚持引擎零依赖，可在 `selectGraphSource` 里预建 Map 再传入。

## 四、细节与建议（P2）

1. **`StudyPage` 的 `words[index]` 潜在越界**（`src/pages/Study/index.tsx` 第 47–49 行）：

```ts
const words = useMemo(() => repository.getModuleWords(moduleId), [moduleId])
const index = state.runtime.currentIndex
const word = words[index]
```

`currentIndex` 的收敛在 `startStudy` / `setCurrentIndex`（`actions.ts` 第 343–356 行）里做了 `Math.min(Math.max(index, 0), maxIndex)`。但存在一个时序窗口：切换 `moduleId` 时，`useEffect`（第 61–68 行）里 `beginStudy` 是异步副作用，`useMemo` 先算出新的 `words`，而 `state.runtime.currentIndex` 仍是上一个模块的下标，若旧下标 > 新模块词数，则 `word === undefined` 渲染一帧空卡。虽然 `useEffect` 随后纠正，但首帧可能闪空。建议在读取处兜底 `const word = words[index] ?? words[0]`，或把 `index` 也纳入 `useMemo` 依赖做收敛。

2. **`isTabPath` 精确匹配对二级路由安全，但对 `/` 的匹配依赖 `pathname === '/'`**（`src/constants/routes.ts` 第 56–58 行）。当前 `MemoryRouter initialEntries={[ROUTES.home]}` 且无尾部斜杠差异，安全。但若未来引入 `/home` 别名或 query 串，需注意 `includes` 会失效。属低风险，记录即可。

3. **`resetAllProgress` 未重置 `settings`**（`src/store/actions.ts` 第 395–402 行）——这是有意为之（清空进度不应动用户发音设置），逻辑正确，无需改，仅提示未来若加「恢复出厂」需区分语义。

4. **`submitGrammarSelfEval` 与 `submitSelfEval` 的 `todayGrammarCount` 判断同样用了 `existing.seen`**（第 279 行），与 P0-1 同源。但语法点是否也走 `markPresented`？当前 `markPresented` 只对词条（Study 页）调用，语法自评（`GrammarDetailPage`）似乎未先 `markPresented`，故 `existing.seen` 可能为 false，`todayGrammarCount` 或能 +1。**建议一并排查**：语法计数是否也有同样的「展示即置 seen」路径，若有则同样失效。

5. **`typing.d.ts` 的 `NativeModules` 是 `declare let`**（第 31 行），而 `storage.native.ts` 第 16 行用 `typeof NativeModules === 'undefined'` 做安全探测——`let` 声明 + `typeof` 探测是正确组合，无 TDZ 风险（`typeof` 对未初始化 `let` 是安全操作）。实现正确，仅记录。

## 五、做得好、应保留的部分 🟢

1. **端口 facade 模式堪称范本**（`engine/storage/index.ts`、`engine/tts/index.ts`）：能力探测（`probe` 吸收异常）→ 平台实现委托 → 内存兜底 → 单例，配合「永不 throw」契约，让 Lynx 原生/Web/纯调试三种环境都能安全运行。`storage.native.ts` / `tts.native.ts` 是唯一引用 `NativeModules` 的文件，红线集中管理到位。

2. **纯函数引擎 + 判别联合类型**（`engine/srs.ts`、`engine/jumpRules.ts`、`types/progress.ts` 的 `JumpDecision`）：状态机、跳转规则、动词变形全部无副作用、可注入时间戳测试，`JumpDecision` 用判别联合穷举 J1–J6，`toStudyEffect` 用 `switch` 穷尽，类型安全且无魔法字符串。

3. **测试分层清晰且断言精确**（261 tests）：单测（`src/*/__tests__`）+ QA 验收测试（`tests/qa/`）+ 数据完整性测试（`data-integrity.qa.test.ts`）三层，覆盖了 NaN、越界、幂等、纯函数不变性、单字匹配防回归等关键边界，尤其 `jumpRules.test.ts` 对 J1「首次遇词」语义裁决的 5 条用例（展示/跳过/已评估/缺省/模糊）验证得极严谨。

4. **注释引用体系化**：几乎每个文件都标注了对应的架构章节（`§2.5`、`§2.6`）、PRD 条款（`§5.5`）、QA 判据（`T04 判据 7`）、team-lead Ruling（`Ruling 1/2/3`），可追溯性极强，团队协作成本低。

5. **hydration 双保险**（`store/index.ts` 第 106–116 行）：`onRehydrateStorage` 解除门控 + 2.5s 看门狗 `setTimeout` 兜底，确保异步存储异常也不会让应用永久停在启动态——这种「回调 + 超时兜底」的健壮性设计值得保留。

6. **`migrateState` 逐字段净化**（`store/persistence.ts` 第 140–147 行）：`readString` / `readNumber` / `readBoolean` 对持久化脏数据逐字段回落默认值，坏数据不崩溃，防御性编程到位。
